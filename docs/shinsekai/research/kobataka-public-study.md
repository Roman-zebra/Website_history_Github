## Instructions to apply to Shinsekai production

The following is our adaptation of the public methods to a historical browser
experience. Specific limits, priorities and acceptance criteria here are project
decisions, not quotations or inaccessible advice from the author.

1. **Payment boundary.** Never buy note articles, membership, tips or access to
   this author's restricted text. Read only public content. Continue the existing
   free-tool/API constraints; an article's recommendations do not authorize
   purchases, model changes, new agents or wider tool access.

2. **Define the intended result.** Before the next asset round, read
   `vibe-modeling-method.md` and the applicable row of `modeling-lessons.md`.
   Brief the subject, era, reference, scope, metres/origin, intended appearance
   and visible acceptance criterion. Historical shapes and the approved empty
   1912 scene take priority over exploratory architecture examples. Keep
   historical, inferred and dream-layer decisions distinct.

3. **Preserve reproducibility.** Record source hashes, generator script, command,
   parameter values, random seeds and output revision. For procedural geometry,
   retain the exact generating inputs alongside the GLB. Original imported
   assets and byte-preserving repairs retain their own source hashes; do not
   replace those inputs with a fresh generator merely for uniformity.

4. **Compare bounded candidates.** Use named baseline and numbered optional
   derivatives. For parameter tuning, begin with three useful settings of one
   variable while keeping all other settings fixed. Do not reproduce the
   thousand-model experiment. The current timber round already offers
   roughness-only, colour-only and combined modes; finish those matched
   comparisons before changing another visual cause.

5. **Look at the results.** For each changed issue, inspect one close view and
   one context view; at a visual milestone cover the six useful perspectives:
   street hero, roof/landing, upper-room wide, cloth contact, timber detail and
   entry route. Reuse fixed cameras, light, exposure and size. Point to the
   visible defect and state its cause hypothesis before revising. File existence,
   changed pixels and validator success do not establish visual improvement.
   Keep direct Blender/browser output as the verification image. An enhanced
   illustration can be a separate concept image, never geometry or runtime
   evidence.

6. **Handle timeouts with evidence.** Before repeating an export or capture,
   inspect outputs for the current run: source revision, timestamp, PNG size,
   expected dimensions, file readability and hash. Check the running process or
   scene when the result is unknown. Existing or stale files are not proof of
   the requested result. Record a completed output if independently verified;
   retry only the missing or failed step after accounting for its state.

7. **Serialize stateful work.** Run scene mutations, simulation, exports and
   saves in a given Blender scene in sequence. Use separate private output
   directories for alternatives. Preserve retained and rejected candidates;
   promote a verified change through the existing sole-writer main workflow.
   Do not copy destructive scene-clearing examples into the production scene.

8. **Improve repeated work selectively.** Reuse setup/capture/save helpers where
   duplication is demonstrated. Optimize expensive generated repetition with
   direct meshes or runtime instancing only after checking actual geometry,
   material, UV and animation invariants. Measure the relevant tool/renderer
   cost; a faster export does not imply better runtime FPS. Recheck saved scene
   persistence after changing authoring persistence, using the existing verifier.

9. **Turn failures into useful notes.** For each resolved issue, record trigger,
   failed attempt, verified fix, applicable conditions and code/receipt location.
   Consult that entry before repeating the operation. If two comparable visual
   revisions leave the same defect, revisit selection, geometry, units or the
   method before another parameter tweak. This two-revision checkpoint is our
   conservative production rule, not a claim about the source articles.

10. **Continue current work in order.** Finish timber comparisons and both
    rendering backends' relevant save/reload/disposal checks. Then address the
    retained cloth candidate's broad silhouette/post occlusion with pin,
    hardware and exported-contact invariants. Keep the remaining lift-car props
    and full approach-route inspection open; doorway-only ray success does not
    settle the whole route. Do not reopen Claude-owned tasks or replace proven
    source geometry for aesthetic experimentation.

Use existing test/build and publication checks. Record actual visual decisions,
pending qualified performance and next work in the shared production state.
Continue the existing Claude conservation/batched review arrangement. No new
scheduler or recurring reading task is requested.
